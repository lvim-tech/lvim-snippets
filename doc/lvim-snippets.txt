1. INTRODUCTION                                          *lvim-snippets-intro*

lvim-snippets is the snippet engine of the lvim-tech set: collections in
three formats (VS Code JSON, SnipMate, LuaSnip syntax) behind ONE engine —
discovery by file extension under configurable roots (recursive), lazy
parsing per filetype, format priority you control. It registers a completion
source into lvim-cmp through the public register_source API (no wiring), and
ships the :LvimSnippets picker: the current buffer's snippets with a live
body preview, insert-at-the-cursor on confirm.

==============================================================================
2. REQUIREMENTS                                   *lvim-snippets-requirements*

  • Neovim >= 0.11
  • lvim-utils (setup() merge)
  • lvim-ui — optional, the :LvimSnippets picker
  • lvim-cmp — optional, snippet completion (the source registers itself)
  • `.lua` collections are read by the plugin's own shim (VS Code / SnipMate
    need nothing)

==============================================================================
3. SETUP                                                 *lvim-snippets-setup*

                                                       *lvim-snippets.setup()*
require("lvim-snippets").setup({opts})

Merges {opts} into the LIVE config in place (every reader
`require("lvim-snippets.config")` sees the effective values), drops the
engine caches (discovery re-runs lazily against the new paths/formats),
registers the "snippets" source into lvim-cmp (when installed and
`cmp.enabled`), and installs the :LvimSnippets command. Call it after
lvim-cmp is available so the registration lands; safe to call again at
runtime to re-point the collection roots. >lua
    require("lvim-snippets").setup({})
<

4. FORMATS AND DISCOVERY                               *lvim-snippets-formats*

Three formats, discovered by file EXTENSION: VS Code (`<ft>.json`, or a
`package.json` manifest's `contributes.snippets`), SnipMate (`<ft>.snippets`,
parsed here — no dependency), and LuaSnip syntax (`<ft>.lua`, run through the
installed). `<ft>` is the filetype; the language "all" applies everywhere.

Folders are fully config-driven — `paths` is the list of roots to scan
(default `{ stdpath("config")/snippets }`; setting your own REPLACES it).
Each root is walked RECURSIVELY, so snippets can be organised in nested
subfolders by type/purpose (`languages/lua.json`,
`frameworks/web/react.snippets`) — the directory names are yours, the
FILENAME sets the filetype. A directory carrying a `package.json` manifest is
a self-contained VS Code collection: the manifest owns its layout (it is not
descended further).

`formats` lists the enabled formats in PRIORITY order (omit one to disable
it); the rank is the equal-fuzzy tiebreak in lvim-cmp. Files parse lazily,
once per filetype per session — `reset()` (or a new `setup()`) picks up new
files on disk.

Expansion goes through the plugin's OWN session engine, not |vim.snippet| —
that is what makes nested placeholders, variables, choices and transforms
work, none of which |vim.snippet| implements. Tabstops jump with <Tab> /
<S-Tab> (lvim-cmp's keys); a placeholder arrives SELECTED, so typing replaces
it. The session ends at the exit stop, or when the cursor leaves the snippet.

Transforms (`${1/regex/replacement/flags}`) are matched with Vim's own regex
engine, so alternation, the quantifiers, non-greedy `+?` and up to nine
capture groups all work, as do the replacement forms `${1:/upcase}`,
`${1:+text}`, `${1:-text}` and `${1:?a:b}`. A regex Vim cannot express —
lookaround, `\b`, more than nine groups — is SKIPPED rather than half-applied,
leaving the source text untouched.

Backtick / python interpolations in SnipMate bodies are NOT evaluated; they
pass through literally.

5. POSTFIX RULES                                       *lvim-snippets-postfix*

A postfix rule is a snippet whose trigger is a LUA PATTERN and which fires AS
YOU TYPE — no completion menu, no accept key: >lua
    { trigger = "([%w_]+)%.par", body = "($1)$0" }   -- foo.par  ->  (foo)
    { trigger = "(.+)%.r",       body = "return $1$0" }
<
The trigger is matched against the text BEFORE the cursor, anchored to its
end; its captures are addressable as `$1`, `$2`… in the body. The LONGEST
trigger wins, so a specific rule is never shadowed by a looser one. A rule
lives in `postfix.rules` (see |lvim-snippets-config|) — added there directly,
or registered by a `.lua` collection's regex-triggered snippets as it loads,
or by a plugin that owns a rule set of its own.

Fields: >lua
    { trigger = "…",   -- Lua pattern (required)
      body    = "…",   -- snippet body, or fun(caps: string[]): string
      desc    = "…",   -- shown in :checkhealth
      ft      = "tex", -- filetype or list (default: every filetype)
      when    = function(ctx) return true end }
<
                                                          *lvim-snippets-when*
`when` is an extra CONDITION about the buffer — the question no pattern can
express: "only inside a maths formula", "not in a comment", "only where the
parse tree says X". It receives >lua
    { buf, row, col, line, from }
<
with every coordinate 0-BASED: `row`/`col` are the cursor, `line` is the whole
line, and `from` is the byte column the matched trigger starts at. Returning
anything but `true` declines the rule.

The predicate is evaluated WHILE MATCHING, not after a winner is picked, so a
rule that declines does not shadow a looser rule that would fire. It runs on
every insert-mode text change, so it must be cheap — and it runs in a pcall: a
broken predicate declines its own rule instead of breaking insert mode.

Rules only fire while `postfix.enabled` is true; `:checkhealth` reports the
engine's state, the rule count and how many rules are conditional.

6. COMPLETION (LVIM-CMP)                                   *lvim-snippets-cmp*

With lvim-cmp installed, setup() registers a "snippets" source through
lvim-cmp's public register_source API — lvim-cmp itself carries no snippet
code. Each record maps to one completion item: prefix → label/filter text,
body → snippet-format insert text, description + fenced body (or the
docstring) → the documentation float, and the format-priority rank encodes
into the item's sort_text so equal-fuzzy snippets tiebreak by format. A
record's body rides on the item — lvim-cmp's accept expands it
through the plugin's own session engine.

The source's per-source options inside lvim-cmp (merge `priority`, the
`min_keyword_length` floor) come from the `cmp` config block; `cmp.enabled =
false` skips the registration entirely.

7. THE PICKER                                           *lvim-snippets-picker*

                                                               *:LvimSnippets*
>vim
    :LvimSnippets                 " float (the default)
    :LvimSnippets area            " the minibuffer / cmdline zone
    :LvimSnippets bottom          " a bottom dock
<
The current buffer's snippets (its filetype + "all") in the canonical lvim-ui
panel: column-aligned prefix + description rows and a live BODY preview
beside the list (treesitter-highlighted by the snippet's language; the
rendered body — when available). A layout token given
anywhere on the command overrides `picker.layout` and sticks for the session.

Keys inside the panel:

  j / k (Down/Up)   move between the snippets (the preview follows)
  <C-l> / <C-h>     move between the list and the preview panel
  <Tab>             toggle the preview panel
  <C-j> / <C-k>     move between sectors (content · footer)
  <CR> / <Space>    insert the focused snippet at the cursor — the panel
                    closes, the snippet expands, the first tabstop is entered
  q / <Esc>         close

8. API                                                     *lvim-snippets-api*

require("lvim-snippets").setup({opts})    see |lvim-snippets.setup()|

                                                         *lvim-snippets.get()*
require("lvim-snippets").get({ft})
        The ranked NEUTRAL snippet records for a filetype (default: the
        current buffer's) — its own files + "all", in format-priority order.
        Each record: >
            { prefix, body, description?, name?, ft, kind, rank,
              docstring?, expand? }
<        `kind` is "vscode" | "snipmate" | "luasnip"; `rank` is the format's
        priority index (1 = highest); `docstring` is the rendered body.

                                                      *lvim-snippets.expand()*
require("lvim-snippets").expand({record})
        Expand a record at the cursor, through the plugin's own session
        engine — every record, every format.

                                              *lvim-snippets.register_paths()*
require("lvim-snippets").register_paths({paths})
        Register collection roots a PLUGIN ships (a string or a list), scanned
        AFTER the user's own `paths` — so a plugin can never outrank or
        replace what you configured. Idempotent (an already known root is
        ignored) and order-independent: a new root drops the discovery cache,
        whenever it arrives. Returns how many roots were added. >lua
            require("lvim-snippets").register_paths(dir .. "/snippets")
<
                                                       *lvim-snippets.paths()*
require("lvim-snippets").paths()
        Every collection root in priority order: the configured ones, then
        the registered ones.

                                                       *lvim-snippets.reset()*
require("lvim-snippets").reset()
        Drop the discovery + parse caches (paths/formats changed, new files
        on disk) — discovery re-runs lazily.

                                                       *lvim-snippets.stats()*
require("lvim-snippets").stats()
        Registry statistics: file/language counts per format, unparsable
        files, per-format counts (what :checkhealth shows).

9. CONFIGURATION                                        *lvim-snippets-config*

The full default config (every option at its default): >lua
    require("lvim-snippets").setup({
        paths = { vim.fn.stdpath("config") .. "/snippets" },
        formats = { "vscode", "snipmate", "luasnip" },
        cmp = {
            enabled = true,
            priority = 80,
            min_keyword_length = 1,
        },
        picker = {
            layout = "float",
            preview = true,
            preview_side = "right",
        },
        postfix = {
            enabled = true,
            rules = {},
        },
    })
<
  paths          collection roots (recursive). Your list REPLACES the default
                 (a clean array merge) — nothing is hardcoded.
  formats        enabled formats in PRIORITY order; omit one to disable it.
  cmp.enabled    register the "snippets" source into lvim-cmp on setup().
  cmp.priority   the source's merge rank among lvim-cmp sources.
  cmp.min_keyword_length
                 per-source keyword floor inside lvim-cmp.
  picker.layout  :LvimSnippets default layout: "float" | "area" | "bottom".
  picker.preview show the body preview panel beside the list.
  picker.preview_side
                 initial preview placement: "right" | "left" | "above" |
                 "below".
  postfix.enabled
                 the as-you-type pattern trigger engine (|lvim-snippets-postfix|).
  postfix.rules  the rules themselves — empty by default: a `.lua`
                 collection's regex-triggered snippets and a plugin's own rule
                 set register themselves here.

==============================================================================
10. HEALTH                                               *lvim-snippets-health*

Run `:checkhealth lvim-snippets`. It reports the Neovim requirement, the
shared dependencies (lvim-utils, lvim-ui), the discovered collections
(per-format file counts and the active priority order), the collection roots
a plugin registered, unparsable files, `.lua` files whose nodes cannot be
translated (they are skipped until it is), the postfix engine (its state, the
rule count and how many rules carry a `when`), whether the "snippets" source
registered into lvim-cmp, and validates the live config.
